_For architects: what personal data the pass service holds and for how long, how secrets and the API are protected, which risks the owner accepted, and how GitHub access stays read-only._

Each section is one decision with four parts: the context, the decision, why, and the trade-off. Where a later decision or the code changed it, the section says so. The [Key decisions](Key-Decisions) page lists every decision on every theme.

## Personal data on the server

**Context:** The Apple update service and the [hand-off](Glossary#hand-off) mean the [Compass API](Glossary#compass-api) holds some personal data, which South Africa's POPIA covers. The responsible party is the owner, acting personally. No human reads server data in normal operation; the owner's administrator access is for emergencies only.

**Decision:**

- **Keyed hashes, not identifiers.** The caller is stored as an HMAC-SHA256 of the [AWS Builder ID](Glossary#aws-builder-id) `sub`, and a device as an HMAC-SHA256 of Apple's device library identifier. Each purpose has its own key, derived from a secret pepper with HKDF ([packages/pass-service/src/security/hashing.ts](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/packages/pass-service/src/security/hashing.ts)). The pepper is in Secrets Manager, generated by the owner's script and never by Terraform, so it is not in Terraform state.
- The Apple authentication token is derived per pass and only its SHA-256 is stored. The hand-off id is stored only as a SHA-256. Pass serial numbers are random UUIDs.
- **Lifetimes:** a pass record lives until the session ends plus 24 hours; a device registration goes on unregister, on an APNs "invalid token" reply or at pass expiry; a hand-off lasts 15 minutes; a rate counter lives until its one-hour window ends plus 2 minutes. Reads check the expiry; DynamoDB [TTL](Glossary#ttl) only cleans up.
- **Apple's fixed paths:** the PassKit paths contain the device library identifier and the serial number, so API access logs keep the route template only, CloudFront standard logs are off, and WAF logging and request sampling are off.
- **No identifiers in logs:** the Lambdas write one log line per request from an allowlist (request id, route template, status, latency, outcome). Log groups keep 14 days.
- **`forget_me`:** `DELETE /api/v1/me` voids every pass of the caller and deletes their pass records, device registrations, hand-offs and rate counters. The local tool also deletes the schedule snapshot, the issued-pass record and the generated files.
- **No backups hold erased data:** point-in-time recovery is off on the table ([infra/modules/data/main.tf](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/infra/modules/data/main.tf)).

**Why:** The server keeps the least it needs to update passes, and an erasure is a real erasure.

**Trade-off:** Push tokens are stored as they are, because they are needed to push, so the roles are least privilege and the table is encrypted at rest. Google keeps its own copy of a saved pass object (inactive after a void), which the privacy text says. See [Data and privacy](Data-and-Privacy).

## The Google Wallet key in Secrets Manager

**Context:** The pass service calls the Google Wallet API to insert and update pass objects and to sign save links, so it needs a Google credential at runtime. Secrets must never be committed, output by Terraform or echoed.

**Decision:**

- The Google Wallet service account key lives in the Secrets Manager secret `compass/<env>/google-wallet`.
- Terraform creates the empty secret. The owner loads the value out of band with [scripts/load-secrets.sh](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/scripts/load-secrets.sh), which reads from files and never echoes.
- The Lambdas read the secret at runtime and cache it in memory.
- The Google issuer and pass class are created by the owner-run [scripts/google-wallet-class.mjs](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/scripts/google-wallet-class.mjs), not by Terraform.

**Why:** The key never appears in the repository, in Terraform state or in a log.

**Trade-off:** The key is a stored, long-lived credential until workload identity federation replaces it, which is a later improvement. The secret is a [retained resource](Decisions-Infrastructure#retained-resources). See [Secrets](Secrets).

## API key enforced at API Gateway

**Context:** The Compass API runs on API Gateway REST behind CloudFront and WAF. The regional `execute-api` address cannot be switched off, so a direct call skips WAF, the rate rules and the kill switch. The Lambdas already refused requests without the CloudFront origin-verify header, but each direct call still started a Lambda.

**Decision:**

- The contract adds an `api_key` scheme (header `x-api-key`) to every operation, all 16 of them. API Gateway enforces it before any Lambda runs.
- CloudFront adds the key as a custom origin header and overwrites any value a viewer sends. Viewers never see or send it.
- The ID token and Apple authentication schemes in the contract stay documentation only; the Lambdas verify those.
- The origin-verify check stays as defence in depth.

**Why:** A direct call to the `execute-api` address gets a 403 from API Gateway and costs nothing.

**Trade-off:** The key value sits in the CloudFront configuration and in HCP Terraform state (accepted in [Accepted residual risks](#accepted-residual-risks)), and is rotated with the origin-verify value. The three contract copies must stay byte-identical.

## A reviewed allowlist for npm audit

**Context:** CI ran `npm audit --omit=dev --audit-level=high`, which fails on any high or critical advisory in production dependencies. On 16 October 2026 it reported three advisories, all reaching the project only through `passkit-generator` 3.7.0, the Apple Wallet library: one in node-forge signature verification, which passkit-generator never calls, and two in joi, which passkit-generator pins exactly. An npm override for joi did not take effect at the time.

**Decision:**

- [.github/scripts/audit-check.mjs](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/.github/scripts/audit-check.mjs) runs `npm audit --omit=dev --json` and fails on any high or critical advisory whose id is not on the allowlist.
- The allowlist holds exactly those three advisory ids, keyed by advisory and not by package, so any new advisory still fails the build. They are printed as a warning on every run.
- Pass-service production code may not import node-forge (an ESLint rule); tests use it only to make throwaway certificates.
- The pass date fields are bounded (at most nine fraction digits, 35 characters), and only canonical dates reach passkit-generator, which closes the joi date issue.

**Why:** It keeps the audit gate strict for everything new while the library's own fix was not available.

**Trade-off:** Accepted risk stays in the build until the ids are removed, so the allowlist is reviewed at every release gate and on every passkit-generator upgrade.

**Today:** The underlying issues are fixed. On 31 October 2026 the project moved to node-forge 1.4.2 and, through a nested override in the root [package.json](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/package.json), to joi 17.13.9, after CI found six new high advisories. On 2 November 2026 `npm audit --omit=dev` reported no advisories at all. The three ids were still on the allowlist but matched nothing. On 4 November 2026 they were removed from the allowlist and from `.trivyignore`, so both lists are empty and every high or critical advisory fails the build. The mechanism stays: an advisory goes back on the list only with a new review recorded here.

## Accepted residual risks

**Context:** On 17 October 2026 several streams were built and reviewed in parallel. Every High finding was fixed and re-reviewed. A few risks could not be closed in code at a cost worth paying for a hackathon project, or needed an owner action first.

**Decision:** The owner accepts these risks, and the release gate checks each one:

1. **Shared signing material.** Dev and prod use the same Apple Pass Type ID certificate and the same Google Wallet service account. Only the owner can start plans and applies (no VCS trigger, no speculative plans, no auto-apply), and the plan and apply roles are denied reading secret values.
2. **The plan role can read the API key value.** Denying it would break every plan, because Terraform reads the key on refresh. The API key and the origin-verify value are also in HCP Terraform state and the CloudFront configuration. Mitigation: restricted state access, owner-only runs and rotation on any access change.
3. **Provider lock files.** Resolved: the lock files of the three Terraform roots are committed for Linux, Windows and macOS.
4. **[Simulated mode](Glossary#simulated-mode) for judges and contributors.** The server defaults to live mode. `COMPASS_MODE=simulated` selects simulated mode, which `reinvent-compass demo`, the tests and the contributor [.env.example](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/.env.example) use. Every simulated result is labelled, a warning is logged, and simulated mode is refused when `NODE_ENV` is production unless `COMPASS_ALLOW_SIMULATED=1` ([packages/core/src/api/client-context.ts](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/packages/core/src/api/client-context.ts)).
5. **Estimated walking times.** AWS publishes no per-pair walking times, so [data/venues.json](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/data/venues.json) holds researched, sourced estimates with a 30-minute floor.
6. **TLS 1.0 on the CloudFront default certificate.** Resolved by the [custom domain](Decisions-Infrastructure#a-custom-domain-for-the-site-and-the-api): viewers get TLS 1.2 or later.
7. **The name uses the "re:Invent" trademark.** The owner kept "re:Invent Compass", because the entry is for AWS's own challenge and the name says what the tool is for. Mitigations: the NOTICE, README, site footer and [Disclaimer](Disclaimer) say Compass is independent and not affiliated with AWS; every pass carries an UNOFFICIAL PASS note ("This is not a ticket. Your re:Invent badge is your official ticket. Bring it to every session."); no AWS logo or artwork is used in the product. The planned fallback, if AWS or the organisers ask, is to rename to "Compass for AWS re:Invent".

**Why:** Each risk is written down with its mitigation, so the release gate can check it and a later change can reopen it.

**Trade-off:** Any change to the deploy model (a VCS trigger, auto-apply or another operator) reopens the first risk and needs separate dev credentials.

**Later:** The third and sixth items were resolved after the first review (the lock files were committed, and the [custom domain](Decisions-Infrastructure#a-custom-domain-for-the-site-and-the-api) replaced the default certificate), and the seventh was added on 22 October 2026 after the pre-release review.

**Today:** The fifth item's first wording, that an impossible connection based on an estimate only warns and never blocks, no longer holds in full. In [packages/core/src/rules/connections.ts](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/packages/core/src/rules/connections.ts), an impossible connection on an estimated walk blocks when the attendee would be late even at half the estimated walk, and only warns otherwise. See [Guardrail rules](Guardrail-Rules).

## A read-only GitHub App for the tech scan

**Context:** The owner added "your tech and your GitHub" on 20 October 2026: Compass learns which technologies an attendee works with from their GitHub repositories, so `find_sessions_by_tech` and `plan_week` can suggest sessions. The requirement was that Compass reaches GitHub only through a [GitHub App](Glossary#github-app), so the token can never write.

**Decision:**

- A public GitHub App, "re:Invent Compass (unofficial)", with Contents: read and Metadata: read only. No webhook, no callback URL, no client secret and no private key. Device flow and expiring user tokens are on.
- The client id and the app slug are public build constants in [packages/mcp-server/src/config/github.ts](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/packages/mcp-server/src/config/github.ts). `COMPASS_GITHUB_CLIENT_ID` and `COMPASS_GITHUB_APP_SLUG` replace them for a self-hosted app; the hosts stay fixed.
- The attendee picks accounts and repositories when installing the app. Before any content is read, they confirm a message naming the accounts and up to 20 repositories. A client that cannot ask is refused.
- One repository archive at a time, in a worker with a 60-second budget. The download must redirect to `codeload.github.com`, and the token is not sent there. The archive is unpacked in memory, capped at 100 MB compressed and 500 MB unpacked.
- Only technology and service keys reach the local [tech list](Glossary#tech-list). Archives and file contents are never written to disk, and repository text never reaches the model.

**Why:** Read-only by construction, so even a stolen token cannot change code. The attendee chooses the repositories, no secret ships, and tokens expire (8 hours for access, 6 months for refresh).

**Trade-off:** Compass cannot revoke a user token itself, because that needs a client secret it does not have. `disconnect_github` and `forget_me` delete the local tokens and tell the attendee where to remove the install and the authorisation on GitHub. Anyone can point Compass at another app, which Compass cannot check is read-only, so it prints a warning.

## GitHub token handling

**Context:** The device flow gives Compass an access token (8 hours) and a refresh token (6 months). A stolen token could read the repositories the app is installed on.

**Decision:**

- Each token has its own OS keychain entry (service `reinvent-compass`, accounts `github-access` and `github-refresh`), through `@napi-rs/keyring`. On Linux the store is the Secret Service, never the kernel keyring ([packages/core/src/github/token-store.ts](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/packages/core/src/github/token-store.ts)).
- With no keychain, or after any keychain error, tokens are held in process memory only. Nothing is written to a file.
- The access token is refreshed when 60 seconds or less remain. Two refreshes of the same token share one call. A refresh that finishes after a disconnect or a new sign-in does not save. If GitHub rejects the refresh token, the store is cleared.
- Tokens go only to `github.com` and `api.github.com`.
- Every token loaded or saved is registered with the one redactor ([packages/core/src/redact/redact.ts](https://github.com/henniefrancis/aws-re_invent-compass/blob/develop/packages/core/src/redact/redact.ts)), which removes it from every log line and error.
- `disconnect_github` clears both tokens and keeps the tech list. `forget_me` does the same after the pass service confirms the passes are voided, and also deletes the tech list. `sign_out` ends the Builder ID session only and leaves GitHub connected.

**Why:** The token is kept where the OS protects it, sent only where it is needed, and never printed.

**Trade-off:** Without a keychain, the attendee connects again after every restart. Compass cannot revoke the token on GitHub. Whether GitHub should stay connected after `sign_out` was left to the owner; the code keeps it connected.
